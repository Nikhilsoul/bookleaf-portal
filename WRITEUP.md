# Write-up: BookLeaf Author Support Portal

**What I prioritised.** The brief weights AI integration and architecture highest, so I built the ticket loop end to end first (author submits → instant ticket → AI triage → admin drafts/edits/sends → author sees it live), then hardened it. The principle throughout: *the AI accelerates the ops team but is never on the critical path*. A ticket is created and returned before any LLM call; triage runs in the background; every AI step has a deterministic fallback (rules classifier, template draft built from the same account data) and the admin can always write manually.

**AI design.** Two small calls with different cost profiles. Classification is KB-free and capped at 120 output tokens. Drafting sends only the KB section for the ticket's category, one calibration reply, and the specific book's facts, not the whole knowledge base or full history. Numbers that matter (next payout cycle, ₹1,000 roll-over, never-paid, in-production) are computed in code and passed as flags so the model explains instead of calculating, which keeps replies accurate and specific, as the tone guide requires. Drafts are cached per ticket, outputs are schema-validated, a circuit breaker protects against provider outages, and all calls are logged (tokens, latency) for cost visibility. Admin overrides are authoritative and never overwritten by later AI output.

**Trade-offs.** SQLite + in-process SSE + a no-build vanilla frontend: minimal moving parts so reviewers can run it in one command, at the cost of single-instance scaling and a plain UI (the brief says function over polish). Attachments are UI-only. Priority combines LLM judgement with a code-level policy floor (ISBN errors ≥ High), trading a little flexibility for predictability on rules the business has stated.

**Product thinking.** Queue sorts by urgency then age with a 48h waiting marker; the admin sees the author's actual royalty/status facts beside the draft; authors get a plain-language note when pending royalty is under the payout threshold or when a book is still in production; replying auto-assigns; an author reply reopens a resolved ticket and flags the draft as stale.

**Evolving to production.** Postgres + Redis pub/sub for multi-instance real-time; live integrations to royalty/production systems for context; httpOnly-cookie sessions, password reset, audit log; S3 uploads; email/WhatsApp notifications; an evaluation set for classification accuracy with confidence-based routing; tracking admin edit-distance on drafts to tune prompts; prompt caching and batching at 1,200+ tickets/month scale; SLA timers per priority and a knowledge-base editor so policy changes don't need a deploy.
